# Spec

요구사항을 받아 **검증 가능한 GOAL**로 바꾼다. 전체 흐름은 `.claude/skills/task/SKILL.md`에 있다.

**코드를 고치지 않는다.** 읽고 분석만 한다. 구현은 `implement`가 맡는다. 여기서 한 줄이라도 고치면 뒤 단계에서 누가 쓴 변경인지 가려지지 않는다.

## 산출 모드는 둘이다

| 모드 | 언제 | 산출물 |
|---|---|---|
| 질문 | 요구사항에 애매한 점이 하나라도 있을 때 | 질문 목록만. `task.md`를 쓰지 않는다 |
| 작성 | 애매한 점이 없을 때 | `task.md` 한 파일 |

- **애매하면 추측해서 채우지 않는다.** 추측으로 채운 GOAL은 승인 단계에서 사용자가 읽고도 그럴듯해 통과하고, 구현이 끝난 뒤에야 틀렸다는 것이 드러난다. 그 시점의 교정 비용이 가장 비싸다.
- 에이전트는 사용자에게 직접 물을 수 없다. 그래서 **애매함을 이 단계에서 질문으로 모아** 오케스트레이터가 대신 묻게 한다. 뒤 단계에서 생긴 애매함은 물어볼 통로가 없다.
- 질문에 답을 받으면 같은 세션에서 이어 `task.md`를 쓴다.
- **질문이 4개 이상이면 요구사항이 덜 정리된 신호다.** 질문을 그대로 보내는 대신 범위를 쪼갤 것을 제안한다. 한 번에 넷을 물어 답을 넷 받으면, 그 답들이 서로 맞물리는지 아무도 확인하지 않은 채 구현이 시작된다.

## task.md

경로는 `.claude/tasks/SHI-<번호>/task.md`. 절은 아래 여섯 개다.

```markdown
## 배경
왜 이 작업을 하는가. 관련 Linear 이슈·PR·대화.

## 환경
작업 디렉터리·브랜치·베이스 커밋, 이미 깨져 있는 것, 플랫폼 제약.

## GOAL
1. <검증 가능한 완료 조건>
   - 검증: `<복사해서 바로 실행할 수 있는 명령>` → <기대 결과>
2. ...

## 비목표
이번에 하지 않는 것. 무시할 것. 판단이 갈리는 지점의 분기별 행동.

## 제약
지켜야 하는 규칙·파일·경로. 건드리면 안 되는 것.

## 참고
명령으로 확인할 수 없지만 알아두면 좋은 것.
```

## 프롬프트 정밀도

구현·검증 에이전트는 **`task.md`에 적힌 것만 안다.** 세션도 화면도 공유하지 않는다. 적지 않은 것은 에이전트가 스스로 정하고, 스스로 정한 것은 승인받지 않은 것이다. 아래 네 절은 모두 "에이전트가 정하게 두지 않는다"는 한 가지를 위한 것이다.

### `## 환경`

- **워크트리 절대 경로, 브랜치 이름, 베이스 커밋 해시.** 에이전트는 자기가 어디서 일하는지 프롬프트로만 안다. 경로가 없으면 메인 작업 디렉터리에서 고칠 수 있고, 베이스 커밋이 없으면 diff의 기준이 어긋난다.
- **이미 깨져 있는 것.** 지금 실패 중인 테스트, 꺼져 있는 컨테이너처럼 이번 작업과 무관한 실패를 미리 알린다. 이것이 없으면 에이전트가 무관한 실패를 쫓느라 시간을 버리고, **멀쩡한 코드를 고친다.**
- **플랫폼 제약.** Windows라 PowerShell과 Bash 문법이 다르다. Docker가 떠 있어야 DB 테스트가 돈다. 8080 포트와 DB·Redis를 모든 워크트리가 공유한다(`.claude/rules/git-workflow.md` "워크트리를 쓸 때 주의").

```markdown
## 환경
- 워크트리: `C:\Users\ks\nss\dev\snsg-be\wt-SHI-31` (브랜치 `chore/SHI-31-delegation-rule`, 베이스 `808e21b`)
- 메인 작업 디렉터리 `snsg-be`는 읽기만 한다
- `UserRedisAdapterTest`는 Docker가 꺼져 있으면 skip된다. 이번 작업과 무관하다
- 셸은 PowerShell이 기본이고 Bash도 쓸 수 있다. `&&`는 PowerShell에서 동작하지 않는다
```

### GOAL의 검증 명령

- **복사해서 바로 실행할 수 있는 전문으로 적는다.** 디렉터리 이동까지 포함한다. "테스트를 돌린다" 같은 서술은 검증 명령이 아니다. 에이전트가 명령을 조립하게 두면 조립한 명령이 실제로 그 항목을 확인하는지 아무도 모른다.
- **기대 결과를 함께 적는다.** 명령만 있으면 **무엇이 성공인지 에이전트가 정한다.**

```markdown
1. 닉네임이 2자 미만이면 `BusinessException(UserErrorCode.INVALID_NICKNAME)`이 난다.
   - 검증: `cd snsg && ./gradlew test --tests '*UserCommandServiceTest'` → 85개 통과
2. 닉네임 중복 확인 API가 이미 쓰는 닉네임에 false를 돌려준다.
   - 검증: `curl -s localhost:8080/api/v1/users/nickname-availability?nickname=tester` → 200, `{"isAvailable":false}`
```

| 나쁜 예 | 왜 안 되는가 | 좋은 예 |
|---|---|---|
| `테스트가 통과한다` | 어떤 테스트인지, 몇 개가 돌아야 하는지 없다. 하나만 돌려도 참이다 | `cd snsg && ./gradlew test` → BUILD SUCCESSFUL, 실패 0 |
| `API를 만든다` | 만들었다는 것을 무엇으로 확인하는지 없다 | `curl -s -o /dev/null -w '%{http_code}' localhost:8080/api/v1/users/me` → `401` |
| `빌드를 확인한다` | 명령이 아니다 | `cd snsg && ./gradlew build` → BUILD SUCCESSFUL |

### `## 비목표`

- **무시할 것을 적는다.** 눈에 띄지만 이번에 건드리지 않을 것(기존 경고, 곁다리 리팩터링 대상, 다른 도메인 파일)을 **이름으로** 적는다. 적지 않으면 에이전트가 "겸사겸사" 고친다. 사용자 요청과 무관한 변경은 diff를 키워 승인 단계에서 봐야 할 것을 가린다.
- **판단이 갈리는 지점은 분기별 행동까지 적는다.** 기준만 주고 행동을 비워두면 에이전트가 정한다.

```markdown
## 비목표
- `UserQueryService`의 deprecated 경고는 그대로 둔다
- `auth` 도메인 파일은 건드리지 않는다
- 기존 테스트의 단정을 고치지 않는다
- 마이그레이션이 이미 머지돼 있으면 새 버전을 더한다. 머지 전이면 기존 파일을 고친다
  (`.claude/rules/package-structure.md` 마이그레이션 절)
```

### 정지 조건

반복 실행되는 작업(같은 프롬프트를 여러 번 도는 작업)이라면 `## GOAL`에 **정지 조건**을 적는다. 언제 끝났다고 보는지, 그리고 **끝내면 안 되는 경우**도 함께 적는다. 끝내면 안 되는 경우를 빼면 에이전트가 중간 상태를 완료로 착각한다.

```markdown
- 정지 조건: `./gradlew test`가 실패 0으로 끝나면 종료한다
- 끝내지 않는 경우: 실패가 줄었지만 0이 아닐 때, 테스트를 지워 실패가 사라졌을 때,
  컴파일이 깨져 테스트가 아예 돌지 않았을 때
```

## 그 밖의 GOAL 작성 규칙

- **"잘 동작하게", "깔끔하게", "읽기 좋게" 같은 표현은 GOAL에 쓰지 않는다.** 무엇을 돌려야 참인지 정해지지 않아, 구현한 쪽과 검증하는 쪽이 각자 다르게 읽는다. 판정이 주관이 되면 기준은 반드시 완화된다.
- **명령으로 확인할 수 없는 항목은 GOAL이 아니라 `## 참고`로 내린다.** GOAL에 남겨두면 검증 단계에서 "대체로 됐다"는 판정이 나올 자리가 생긴다.
- 테스트가 필요한지, 어떤 계층을 어떻게 테스트하는지는 `.claude/rules/testing.md`를 따른다. 테스트하지 않기로 되어 있는 변경에 테스트 통과를 GOAL로 걸지 않는다.
- 파일을 고치지 말아야 하는 범위도 GOAL로 쓸 수 있다. 명령으로 확인되기 때문이다.

```markdown
4. java 파일과 워크트리 밖 파일을 고치지 않는다.
   - 검증: `git status --short` → `.java` 없음, 모든 경로가 워크트리 안
```

- **GOAL에는 결과와 사용자와 합의한 결정만 쓴다.** 결과는 "무엇이 참이면 끝인가"다. 구현 에이전트가 바꿔도 되는 것(클래스·설정 키 이름, 파일 구성, 테스트 메서드 이름, 정확한 변경 파일 목록)은 `## 참고`에 제안으로 내린다.
  - 이유: 검증은 GOAL에 적힌 결과로 해석 차이를 잡고, GOAL에 적히지 않은 설계 품질은 오케스트레이터 재확인과 사용자의 diff 승인이 잡는다. 구현 세부를 GOAL에 박으면 사용자가 승인하는 대상이 spec 에이전트가 정한 세부가 되고, 같은 결과를 다른 형태로 이뤄도 FAIL이 나 재작업이 돈다.
  - "프롬프트 정밀도" 절과 충돌하지 않는다. 그 절이 정밀하게 적으라는 대상은 **환경과 검증 방법**(경로·브랜치·베이스 커밋·검증 명령·기대 결과)이고, 이 규칙이 GOAL에서 빼는 것은 **구현의 형태**다. 어디서 어떻게 확인할지는 정밀하게, 무엇으로 만들지는 구현에 맡긴다.

## `## 제약`

- 지켜야 하는 규칙을 **파일 이름으로 가리킨다.** 규칙 본문을 베껴 적으면 원본이 바뀔 때 두 곳이 어긋나고, 구현하는 쪽은 베껴진 쪽을 믿는다.
- **마지막 줄에 범위 제한 문장을 반드시 넣는다.**

```markdown
## 제약
- 패키지 구조는 `.claude/rules/package-structure.md`를 따른다
- 테스트는 `.claude/rules/testing.md`를 따른다
- 요청에 없는 수정은 하지 않는다. 각 GOAL 항목이 요구하는 것만 건드린다.
```
