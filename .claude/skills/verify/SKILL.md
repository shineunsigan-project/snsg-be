# Verify

`task.md`의 GOAL이 실제로 달성됐는지 **항목별로 판정한다.** 전체 흐름은 `.claude/skills/task/SKILL.md`에 있다.

## 읽기 전용 에이전트로 띄운다

- `Agent` 도구의 `subagent_type: Explore`로 띄운다. 쓰기 도구가 없어 **고칠 수 없다.** 고칠 수 있으면 검증이 아니라 수선이 되고, "조금 손봐서 통과시켰다"가 가능해지면 기준이 저절로 완화된다.
- **사용자가 `/verify`를 직접 불러도 메인 세션이 직접 검증하지 않고 에이전트를 띄운다.** 작업한 쪽이 검증하면 독립성이 깨진다. 자기가 방금 내린 판단을 전제로 읽게 되어, 빠뜨린 것은 그대로 빠뜨린 채 통과한다.

## 받는 입력

| 받는다 | 받지 않는다 |
|---|---|
| `task.md`의 `## 환경`, `## GOAL`, `## 비목표` | 구현 에이전트(agent2)의 보고 |
| 저장소 (워크트리 경로) | 구현 과정의 대화·판단 |
| `git diff --staged` | |

**agent2의 보고는 받지 않는다.** "테스트를 다 통과시켰다"는 보고를 먼저 읽으면 그것을 전제로 확인하게 된다. 받는 것은 GOAL과 저장소, `git diff --staged` 뿐이다.

## 판정 형식

GOAL 항목마다 아래 네 줄을 적는다.

```
[1] docs/openapi.yaml에 새 엔드포인트가 반영된다
    명령: cd snsg && ./gradlew test --tests '*OpenApiSpecTest*'
    결과: BUILD SUCCESSFUL, 1 test passed
    판정: PASS

[2] 닉네임 2자 미만이면 INVALID_NICKNAME이 난다
    명령: cd snsg && ./gradlew test --tests '*NicknameTest*'
    결과: 테스트는 통과하나 2자 미만 케이스가 없다. 빈 문자열만 검증한다
    판정: FAIL — 2자 미만(1자) 케이스 테스트가 없다

전체: FAIL (2번)
```

- FAIL이면 **무엇이 빠졌는지 한 줄**로 적는다. 어떻게 고칠지는 적지 않는다. 고치는 것은 구현 단계의 일이다.
- **하나라도 FAIL이면 전체 FAIL이다.** 부분 점수를 두지 않는다. "3개 중 2개 통과"가 허용되면 남은 하나는 다음 작업으로 밀리고, 밀린 것은 돌아오지 않는다.

## 기준을 완화하지 않는다

- **"대체로 됐다", "의도는 맞다"로 PASS를 주지 않는다.** GOAL 문구와 다르면 FAIL이다.
- GOAL에 검증 명령이 붙어 있으면 **그 명령을 실제로 돌린다.** 코드를 읽어 "맞아 보인다"로 대신하지 않는다. 명령을 돌릴 수 없으면 그 사실을 FAIL 사유로 적는다.
- 명령이 없거나 명령으로 확인할 수 없는 항목이 GOAL에 남아 있으면, 주관으로 판정하지 않고 **GOAL이 검증 불가능하다고 보고한다.** 명령으로 확인할 수 없는 것은 `## 참고`에 있어야 한다(`.claude/skills/spec/SKILL.md`).
- **`## 환경`에 "이미 깨져 있는 것"으로 적힌 실패는 FAIL 사유가 아니다.** 이번 작업 전부터 실패하던 것이고, 그것까지 FAIL로 묶으면 모든 작업이 FAIL이 되어 판정이 의미를 잃는다. 반대로 거기 적히지 않은 실패는 이번 변경이 만든 것으로 본다.

## 테스트 자체를 의심한다

테스트가 통과한다는 것은 테스트가 맞다는 전제에서만 의미가 있다. 이 단계에서 그 전제를 확인한다.

- **`git diff --staged`에서 기존 테스트 파일의 수정·삭제가 있으면 이유가 타당한지 본다.** 통과하지 않는 테스트를 지우거나 단정(assertion)을 느슨하게 바꾸는 것이 가장 흔한 완화 경로다. GOAL이 요구하지 않은 기존 테스트 변경은 사유를 찾을 수 없으면 FAIL이다.
- **새 테스트가 GOAL에 적힌 규칙을 실제로 검증하는지 읽는다.** 테스트 이름이 아니라 본문을 본다. 이름은 GOAL과 같은데 단정하는 값이 다른 경우가 있다.
- **통과하도록 테스트를 맞춘 것이 아닌지 확인한다.** 구현이 내놓는 값을 그대로 기대값에 적으면 무엇을 바꿔도 통과한다. 기대값이 GOAL에서 온 것인지, 구현 결과에서 온 것인지 본다.
- 테스트가 필요한 변경인지, 어느 계층을 어떻게 테스트해야 하는지는 `.claude/rules/testing.md` 기준으로 본다. 그 문서가 테스트하지 않기로 한 것에 테스트가 없다는 이유로 FAIL을 주지 않는다.

## GOAL에 없는 것을 트집잡지 않는다

- **검증 대상은 GOAL이다.** 더 나은 설계, 추가하면 좋을 테스트, 눈에 띄는 다른 개선점은 FAIL 사유가 아니다. 적어 보낼 수는 있으나 판정과 구분해 적는다.
- `## 비목표`에 적힌 것이 되어 있지 않은 것은 정상이다. `## 비목표`를 넘어선 변경이 diff에 있으면 그것이 FAIL이다.
