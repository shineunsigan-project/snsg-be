# Refine docs

이번 작업의 결과를 **다음에 읽는 사람이 알 수 있게** 문서에 남긴다. 전체 흐름은 `.claude/skills/task/SKILL.md`에 있다.

작업은 끝났는데 문서가 예전 상태로 남으면, 다음 세션과 FE 담당자는 낡은 문서를 믿고 움직인다. 코드는 테스트가 지키지만 문서는 지키는 것이 없다. 그래서 이 단계를 따로 둔다.

## 언제 띄우는가

- **verify가 전 항목 PASS를 내고, 오케스트레이터가 재확인을 마친 뒤**에 띄운다. 사용자에게 diff 승인을 받기 직전이다.
  - 이 시점에 두는 이유: 문서 변경이 같은 diff 승인과 같은 PR에 들어간다. CLAUDE.md는 rules·skills 갱신을 진행 중인 작업 브랜치에 함께 커밋하라고 한다.
  - verify보다 먼저 띄우거나 동시에 띄우지 않는다. 검증 중인 diff가 바뀌고, 한 워크트리에 쓰는 에이전트가 둘이 된다.
- 쓰기 가능한 기본 에이전트로 띄운다. 워크트리는 오케스트레이터가 만든 것을 쓴다.

## 받는 입력

| 받는다 | 받지 않는다 |
|---|---|
| 워크트리 절대 경로, `task.md` 경로 | 구현·검증 에이전트의 보고 |
| `git diff --staged` | |
| 오케스트레이터가 정리한 **이번 작업에서 사용자와 합의한 것**, **사용자가 반복해서 지적한 것** | |
| 저장소 밖 기획 문서 경로(있으면) | |

- 에이전트는 사용자와의 대화를 볼 수 없다. 합의와 지적은 오케스트레이터가 사용자 표현에 가깝게 옮겨 준다. 받지 못한 합의를 diff에서 추측해 규칙으로 만들지 않는다.

## 점검할 문서

| 문서 | 무엇을 보는가 |
|---|---|
| `docs/api-guide.md`, `docs/openapi.yaml`, `docs/linear-convention.md` | FE가 읽는 문서다. 이번 변경으로 동작·값·오류 코드·흐름이 바뀌었는데 문서가 그대로인 곳 (`.claude/rules/api.md` 문서 절) |
| `.claude/rules/*.md` | 사용자와 새로 합의한 규칙, 같은 지적이 반복된 것, 이번 변경으로 낡은 예시(클래스·설정 키·경로 이름) |
| `.claude/skills/*/SKILL.md` | 이번 작업에서 반복된 절차, 절차대로 했는데 막혔던 지점과 실제로 통한 방법 |
| `CLAUDE.md` | 위 문서로 보낼 수 없는, 매 세션 알아야 하는 사실만. 짧게 유지한다 |
| 저장소 밖 기획 문서 | **고치지 않는다.** 이번 변경과 어긋나는 곳을 찾아 보고만 한다. 저장소 밖이라 커밋되지 않고, 워크트리 밖 파일은 오케스트레이터가 고친다 |

## 고치는 기준

- **합의된 내용과 코드에서 확인한 사실만 적는다.** 추측성 규칙은 넣지 않는다(CLAUDE.md "에이전트 문서 관리").
- **고친 곳마다 근거가 있어야 한다.** 근거는 diff의 특정 변경, `task.md`, 오케스트레이터가 넘긴 합의 중 하나다. 근거를 댈 수 없으면 고치지 않고 "후보"로 보고한다.
- 규칙 본문을 다른 문서에 베껴 적지 않는다. 파일 이름으로 가리킨다. 베끼면 원본이 바뀔 때 두 곳이 어긋난다.
- 규칙은 rules로, 절차는 skills로 보낸다. CLAUDE.md에 늘어놓지 않는다.
- 기존 문장을 지우거나 뜻을 바꿀 때는 그 문장이 이번 변경으로 틀려졌다는 근거를 보고에 적는다.
- **코드와 `task.md`의 GOAL은 고치지 않는다.** 문서와 코드가 어긋나 코드가 틀린 것으로 보이면 고치지 않고 보고한다. 그건 구현 단계로 돌아갈 일이다.
- `docs/openapi.yaml`은 손으로 고치지 않는다. 코드에서 생성되고 `OpenApiSpecTest`가 대조한다. 어긋나 있으면 보고한다.
- 문서를 고칠 필요가 없으면 아무것도 고치지 않는다. 그것도 정상 결과다.

## 끝내는 방법

- 고친 문서를 `git add`로 스테이징한다. 커밋은 하지 않는다.
- 문서 외의 파일이 스테이징에 새로 섞이지 않았는지 `git diff --staged --name-only`로 확인한다.

## 보고 형식

1. **고친 것**: 파일, 바뀐 내용 한 줄, 근거
2. **점검했지만 고칠 필요가 없던 문서**: 왜 그대로 두었는지 한 줄씩
3. **기획 문서와 어긋나는 곳**: 파일, 위치, 어떻게 어긋나는지(저장소 밖, 오케스트레이터가 처리)
4. **후보**: 근거가 부족해 고치지 않은 것. 사용자가 정할 일이다
