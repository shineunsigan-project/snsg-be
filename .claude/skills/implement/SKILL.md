# Implement

`task.md`를 읽고 **그대로 실행한다.** 전체 흐름은 `.claude/skills/task/SKILL.md`에 있다.

경로는 `.claude/tasks/<issue번호>/task.md`. `## 배경`, `## 환경`, `## GOAL`, `## 비목표`, `## 제약`, `## 참고`를 모두 읽고 시작한다.

`## 환경`에 **이미 깨져 있는 것**이 적혀 있다. 거기 적힌 실패는 이번 작업과 무관하므로 쫓지 않는다. 무관한 실패를 고치려 들면 멀쩡한 코드를 건드리게 된다.

## GOAL을 수정하지 않는다

- GOAL은 사용자 승인을 받은 문장이다. 구현하면서 고치면 승인받은 것과 다른 것이 만들어지고, 검증은 고쳐진 GOAL로 돌아 전부 PASS가 난다. **기준이 사라지는 가장 빠른 경로가 이것이다.**
- GOAL이 틀렸거나 범위 변경이 필요하면 **멈추고 보고한다.** 사용자에게 다시 물어야 할 일이고, 에이전트는 사용자에게 물을 수 없다.
- 구현이 막혀 GOAL을 달성할 수 없을 때도 같다. 비슷한 것으로 바꿔 채우지 않고 멈춘다.

## 범위

| 하는 것 | 하지 않는 것 |
|---|---|
| `## GOAL`에 적힌 변경 | `## 비목표`에 적힌 것 |
| `## 제약`을 지킨 구현 | 요청에 없는 리팩터링·포맷팅·주석 정리 |
| 워크트리 안의 파일 수정 | 워크트리 밖의 파일 수정 |
| `git add`로 스테이징 | 커밋·push·PR |

- **`## 비목표`와 `## 제약`을 넘지 않는다.** 요청에 없는 리팩터링을 하지 않는다. CLAUDE.md "3. Surgical Changes"와 같은 기준이고, 여기서는 diff가 커지면 승인 단계에서 사용자가 봐야 할 것이 묻힌다는 이유가 더해진다.
- **워크트리 밖을 고치지 않는다.** 메인 작업 디렉터리(develop)는 읽기와 조회만 한다(`.claude/rules/git-workflow.md` 2번). 다른 워크트리를 고치면 진행 중인 다른 작업에 변경이 섞인다.
- 테스트는 `.claude/rules/testing.md`를 따른다. 무엇을 테스트하고 무엇을 테스트하지 않는지, 슬라이스 테스트 설정까지 그 문서에 있다.

## 커밋하지 않는다

`git add`로 스테이징까지만 하고 멈춘다.

```bash
git add -A
git status --short
```

- 이유는 `.claude/rules/git-workflow.md` 3번이다. **커밋 전에 사용자가 IDE에서 diff를 확인하고 OK해야 커밋한다.** 이 절차는 사용자와의 대화를 전제하는데, 에이전트는 사용자에게 물을 수 없다. 그래서 커밋 권한을 오케스트레이터에 남긴다.
- 스테이징까지는 해둔다. 새 파일이 Unversioned로 흩어지지 않고 한 묶음으로 보여, 사용자가 diff를 한 번에 본다. 검증 단계도 `git diff --staged`를 본다.
- push와 PR도 하지 않는다. 커밋이 없으므로 올릴 것도 없다.

## 테스트를 돌릴 때

- **DB·Redis·8080 포트는 모든 워크트리가 공유한다**(`.claude/rules/git-workflow.md` "워크트리를 쓸 때 주의"). 다른 작업이 돌고 있을 수 있으니 앱을 띄워둔 채 방치하지 않는다.
- 워크트리에 `snsg/.env`가 없으면 컨텍스트가 뜨지 않는다. 없으면 보고한다. 직접 만들지 않는다. 환경변수 값을 추측해 채우면 테스트는 통과하는데 실제 설정과 다른 상태가 된다.

## 끝낼 때 보고할 것

1. 무엇을 했는지 (고친 파일과 그 이유)
2. **GOAL 항목별로 어떻게 처리했는지.** 번호를 그대로 쓰고, 어떤 변경이 그 항목을 만족시키는지 적는다
3. 실행한 검증 명령과 결과
4. 막힌 것, 판단이 필요한 것

보고는 오케스트레이터에게 간다. **검증하는 에이전트는 이 보고를 받지 않는다.** 보고가 검증의 전제가 되지 않도록 분리되어 있다. 보고를 잘 써서 통과를 받아낼 수 없고, 그럴 필요도 없다.
