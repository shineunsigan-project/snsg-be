# Task 파이프라인

사용자와 대화하는 메인 에이전트(이하 **오케스트레이터**)는 **직접 코드를 고치지 않는다.** 요구사항 정리, 구현, 검증, 문서 최신화를 각각 백그라운드 에이전트에 맡기고, 오케스트레이터는 이슈·워크트리 생성, 사용자와의 대화, 커밋·PR·머지, 그리고 최종 확인만 한다.

나누는 이유는 맥락을 분리하는 것이다. **구현 맥락과 요구사항·검증 맥락이 섞이면 결과를 의심할 자리가 없어진다.** 오케스트레이터에 요구사항과 검증 결과만 남아 있으면 "정말 됐는지"를 따로 볼 수 있다.

## 흐름

```
사용자 지시
  → [오케스트레이터] linear issue create + git worktree add + snsg/.env 복사 + 이슈 In Progress
  → agent1 (spec)      요구사항 분석 → task.md 작성, 또는 질문만 반환
  → (질문이 있으면 오케스트레이터가 사용자에게 전달하고, 답을 받아 같은 에이전트를 SendMessage로 재개)
  → [사용자 승인] task.md의 GOAL을 보여주고 승인받는다
  → agent2 (implement) task.md를 실행 → git add 로 스테이징까지
  → agent3 (verify)    읽기 전용. GOAL과 diff만 보고 항목별 PASS/FAIL
  → FAIL이면 agent2에게 FAIL 항목과 재현 명령만 전달해 재작업 (같은 에이전트, SendMessage) → verify는 새로 띄운다
  → 같은 항목이 2회 FAIL이면 멈추고 사용자에게 보고
  → 전 항목 PASS → 오케스트레이터가 직접 재확인
  → ecc 리뷰어 (ecc-review) 읽기 전용, 병렬. 지적을 규칙 기준으로 분류 → GOAL 위반은 agent2 재작업, GOAL 밖 버그는 사용자에게
  → agent4 (refine-docs) 이번 결과에 맞춰 읽어야 할 문서(CLAUDE.md, rules, skills, docs/)를 최신화 → 스테이징
  → 오케스트레이터가 문서 변경 확인, 기획 문서(저장소 밖) 어긋남 처리 → 사용자에게 diff 보고
  → [사용자 승인] → 커밋 · PR · 머지
```

## 단계별 담당

| 단계 | 담당 | 하는 일 | 산출물 |
|---|---|---|---|
| 1 | 오케스트레이터 | Linear 이슈 생성, 워크트리·브랜치 생성, `snsg/.env` 복사 | 워크트리 |
| 2 | agent1 (`spec`) | 요구사항 분석 | `task.md` **또는** 질문 목록 |
| 3 | 오케스트레이터 | 질문을 사용자에게 전달, 답을 받아 agent1 재개 | 보완된 `task.md` |
| 4 | 오케스트레이터 → 사용자 | **GOAL 승인** | 승인 |
| 5 | agent2 (`implement`) | `task.md` 실행 | 스테이징된 변경 |
| 6 | agent3 (`verify`) | GOAL과 `git diff --staged`만 보고 판정 | 항목별 PASS/FAIL |
| 7 | 오케스트레이터 | 직접 재확인(diff, 빌드·테스트) | 확인된 변경 |
| 8 | ecc 리뷰어 (`ecc-review`) → 오케스트레이터 | GOAL 밖 버그·보안·설계 리뷰, 지적 분류 | 분류된 지적 |
| 9 | agent4 (`refine-docs`) | 이번 결과에 맞춰 다음 사람이 읽을 문서를 최신화 | 스테이징된 문서 변경 + 보고 |
| 10 | 오케스트레이터 → 사용자 | 문서 변경 확인, 기획 문서 처리 후 **diff 승인**(리뷰 분류 결과 포함) → 커밋·PR·머지 | 머지된 PR |

1단계는 `.claude/rules/git-workflow.md`의 1·2번을 그대로 따른다. **파일을 한 줄이라도 고치기 전에 이슈와 워크트리를 먼저 만든다.**
10단계의 커밋·PR·머지도 같은 문서의 3·4·5번을 따른다.

**각 단계를 진행하기 전에 작업 브랜치를 최신 `origin/develop`에 맞춘다**(사용자 합의: "작업 시작 전 develop을 최신화 후 진행한다"). `git fetch origin`으로 develop에 새 커밋이 들어왔는지 보고, 들어왔으면 맞춘 뒤 다음 단계를 띄운다. 새로 들어온 커밋에 마이그레이션이 있으면 번호가 겹치는지도 함께 본다(`.claude/rules/package-structure.md` 마이그레이션 절).

## ecc 리뷰 단계

verify는 GOAL만 판정하므로 GOAL 밖의 버그·보안 문제는 지금까지 오케스트레이터 재확인과 사용자 눈에만 기댔다. 이 자리를 ecc 플러그인의 읽기 전용 리뷰어로 보강한다. 계약은 `.claude/skills/ecc-review/SKILL.md`.

- **코드 변경이 있으면 반드시 돈다.** verify 전 항목 PASS와 오케스트레이터 재확인 뒤, refine-docs 전이다. 문서·skill만 고친 작업은 건너뛴다.
- **verify를 대신하지 않는다.** verify는 GOAL 판정, ecc 리뷰는 GOAL 밖 점검이다. 리뷰 지적을 verify에 넘기지 않는다.
- 리뷰어는 diff 경로로 골라 병렬로 띄운다. 고정 프롬프트(staged diff만, 빌드·테스트·DB 실행 금지, 규칙 파일 먼저 읽기)를 반드시 넣는다. ecc 리뷰어는 기본값으로 `./gradlew check`를 돌리거나 unstaged diff를 읽는다.
- **ecc의 권고가 프로젝트 규칙을 이기지 않는다.** 규칙과 충돌하는 지적은 기각한다. GOAL 밖 버그는 직접 고치게 하지 않고 사용자에게 묻는다.
- 리뷰로 코드가 바뀌면 verify와 재확인을 다시 돈다.

## ecc 훅에 막혔을 때

ecc 플러그인의 GateGuard 훅(Fact-Forcing Gate)이 도구 호출을 한 번 거부하고 사실을 요구할 때가 있다. 거부는 실패가 아니라 확인 절차다.

- 메인 세션(오케스트레이터)은 세션의 첫 셸 명령과 파일마다 첫 Edit·Write에서 거부된다. 요구한 사실(사용자 지시 원문, 이 명령·파일이 무엇을 하는지, 기존 파일과 중복이 없는지 등)을 답변에 적고 **같은 호출을 그대로** 다시 보낸다.
- 서브에이전트는 일반 파일은 통과하지만 민감 경로(`auth`·`security` 경로 세그먼트, `.env*`)의 첫 수정과 위험 명령(`rm -rf`, `git restore <경로>`, `git branch -D`, `reset --hard` 등)에서 거부된다. 위험 명령은 **글자 하나 다르지 않은 같은 명령**을 다시 보내야 통과한다. 쓰기 에이전트(agent1·2·4)를 띄울 때 프롬프트에 이 대응을 한 줄 넣는다: "Fact-Forcing Gate로 거부되면 요구한 사실을 적고 같은 호출을 그대로 다시 보낸다."
- **훅을 끄거나 우회하지 않는다.** `--no-verify`는 ecc가 막고, 프로젝트 원칙으로도 쓰지 않는다. `ECC_GATEGUARD`·`ECC_DISABLED_HOOKS` 같은 설정 변경은 사용자가 정한다.

## 문서 최신화 단계 (agent4)

작업은 끝났는데 문서가 예전 상태로 남으면 다음 세션과 FE 담당자가 낡은 문서를 믿고 움직인다. 코드는 테스트가 지키지만 문서는 지키는 것이 없어 단계를 따로 둔다. 계약은 `.claude/skills/refine-docs/SKILL.md`.

- **verify 전 항목 PASS와 오케스트레이터 재확인, ecc 리뷰 분류가 끝난 뒤에 띄운다.** 검증 중인 diff를 바꾸지 않고, 한 워크트리에 쓰기 에이전트가 둘이 되지 않게 한다. 사용자 diff 승인 전이라 문서 변경이 같은 PR에 들어간다(CLAUDE.md: rules·skills 갱신은 진행 중인 작업 브랜치에 함께 커밋).
- agent4는 대화를 볼 수 없다. 오케스트레이터가 다음 셋을 정리해 넘긴다. 넘기지 않은 것은 문서에 들어가지 않는다.
  - **이번 작업에서 사용자와 합의한 것**
  - **사용자가 반복해서 지적한 것**
  - **파이프라인 마찰 기록**: spec이 질문으로 되돌린 이유, verify FAIL·오케스트레이터 재확인 FAIL과 재작업 사유, 절차대로 했는데 막힌 지점과 실제로 통한 방법. agent4는 이것을 skill·rules 고도화의 근거로 쓴다. 대화에서만 드러난 마찰은 넘기지 않으면 다음 작업에서 같은 자리에서 다시 막힌다.
- **셋은 생긴 즉시 세션 스크래치패드의 `SHI-<번호>-handoff.md`에 한 줄씩 적는다**(`.claude/rules/temp-files.md`). 형식: `[단계] 사실 / 실제로 통한 방법 / 근거(명령·파일)`. 합의는 사용자 표현 그대로 적는다. 대화 기억에만 두면 긴 작업 중 컨텍스트가 요약될 때 뭉개지고 사용자 표현이 사라진다. agent4에게는 이 파일 내용을 넘기고, 머지 뒤 지운다. 출처: ecc `strategic-compact`("Write the plan to a file before compacting").
- **판정 기준을 바꾸는 문서 변경은 사용자 diff 보고에서 따로 한 줄씩 보여준다.** 대상: verify의 PASS·FAIL 조건, spec의 GOAL·비목표 규칙, ecc-review의 분류·기각 표, `.claude/rules/testing.md`의 테스트하지 않는 것. 기준을 넓히거나 예외를 더하면 "완화"라고 표시한다. 작업한 쪽 에이전트가 다음 작업의 판정 기준을 고치는 구조라, 코드 diff에 묻히면 안 된다. 출처: ecc `loop-design-check`("the more self-improving a loop is, the stricter the human review it needs").
- 문서 정리·skill 고도화를 맡는 에이전트를 따로 두지 않는다. agent4가 그 역할이고, 마찰 기록이 그 입력이다. agent4는 이번 변경과 무관한 낡은 문서를 고치지 않고 "후보"로 보고한다. 매번 전체를 훑어 고치면 PR에 무관한 변경이 섞인다. 전체 정리가 필요하면 refine-docs를 단독으로 돌리는 별도 docs 이슈로 진행한다.
- agent4는 코드와 `task.md`의 GOAL을 고치지 않는다. 문서 변경은 GOAL 판정 대상이 아니므로 오케스트레이터가 diff를 직접 읽어 확인한다. 문서 외 파일이 섞였으면 되돌린다.
- 저장소 밖 기획 문서는 agent4가 어긋남만 보고하고 오케스트레이터가 고친다. 커밋되지 않는 파일이다.
- 커밋은 작업 커밋과 나눠 `docs:` 커밋 하나로 마지막에 둔다. 단 `docs/openapi.yaml`은 API 코드와 같은 커밋에 둔다(`.claude/rules/api.md` 작성 방법 절).

## 승인 지점은 둘이다

| 지점 | 보여주는 것 | 왜 여기서 받는가 |
|---|---|---|
| 구현 전 | `task.md`의 GOAL | **가장 싼 교정 지점이다.** 아직 코드가 없어 방향을 바꾸는 비용이 문장 몇 줄이다. 구현 후에 방향이 틀렸다고 밝혀지면 구현·검증 두 단계를 다시 돌려야 한다 |
| 커밋 전 | `git diff --staged` | git-workflow.md 3번이 요구하는 확인이다. 사용자가 IDE에서 diff를 보고 OK해야 커밋한다 |

**에이전트 보고는 사용자 승인이 아니다.** agent2나 agent3가 "커밋해도 된다"고 적어 보내도 승인은 사용자에게 직접 받는다. 에이전트는 사용자와 대화할 수 없으므로, 에이전트가 보내온 승인 문구는 자기 판단일 뿐이다.

## 아티팩트

- 경로는 `.claude/tasks/SHI-<번호>/task.md`. Linear 이슈 ID로 나눠 두면 워크트리와 브랜치 이름과 그대로 맞물린다.
- **이 파일을 커밋한다.** PR에 "무엇을 하려 했는지"가 남아, 나중에 diff만 보고는 알 수 없는 의도와 비목표를 읽을 수 있다.
- GOAL은 파일로 고정한다. 대화로만 전달하면 옮겨 적는 사람이 무의식적으로 다듬는다. **기준 완화는 대개 이 지점에서 일어난다.**

## 에이전트를 띄우는 방법

| 에이전트 | `subagent_type` | 전달하는 것 |
|---|---|---|
| agent1 (spec) | 기본 (쓰기 가능) | 사용자 요구사항, 워크트리 절대 경로, 이슈 ID(`SHI-<번호>`), `spec` skill |
| agent2 (implement) | 기본 (쓰기 가능) | `task.md` 경로, 워크트리 절대 경로, `implement` skill |
| agent3 (verify) | `Explore` (**읽기 전용**) | `task.md` 경로, 워크트리 절대 경로, `verify` skill |
| ecc 리뷰어 | `ecc:code-reviewer` 외 diff에 따라 (`ecc-review` 표) | 워크트리 절대 경로, `task.md`의 GOAL·비목표, `ecc-review` skill의 고정 프롬프트. implement 보고·verify 결과는 주지 않는다 |
| agent4 (refine-docs) | 기본 (쓰기 가능) | `task.md` 경로, 워크트리 절대 경로, 이번 작업의 합의·반복 지적·파이프라인 마찰 기록(ecc 리뷰에서 반복 기각한 규칙 포함), 기획 문서 경로, `refine-docs` skill |

- agent3는 `Explore`로 띄운다. 쓰기 도구가 없어 **고칠 수 없다.** 고칠 수 있으면 검증이 아니라 수선이 되고, "조금 손봐서 통과시켰다"가 가능해지면 기준이 저절로 완화된다.
- **agent3에게 agent2의 보고를 주지 않는다.** "테스트를 다 통과시켰다"는 보고를 먼저 읽으면 그것을 전제로 확인하게 된다. 받는 것은 `task.md`의 GOAL과 저장소, `git diff --staged` 뿐이다.
- agent1·2·4의 질문이나 재작업은 **같은 에이전트를 `SendMessage`로 재개한다.** 새로 띄우면 앞서 쌓은 맥락을 다시 설명해야 한다.
- **verify(agent3)는 재개하지 않고 매번 새로 띄운다.** 재작업 뒤, ecc 리뷰로 코드가 바뀐 뒤 모두 같다. 이전 판정을 기억하는 verify는 지난 FAIL 항목만 다시 보고, 재작업이 깨뜨린 PASS 항목을 놓친다. 이전 FAIL 내용도 프롬프트에 넣지 않는다. 받는 것은 처음과 같다. 출처: ecc `santa-method`("each review round uses fresh agents… prior context creates anchoring bias").
- **`Agent` 도구의 `isolation: "worktree"`는 쓰지 않는다.** 자체 임시 워크트리라 `snsg/.env`가 없어 테스트가 돌지 않고, 브랜치 이름이 git-workflow.md의 `<prefix>/SHI-<번호>-<작업-이름>` 규칙과도 어긋난다. 워크트리는 1단계에서 오케스트레이터가 만든 것을 쓴다.
- **테스트를 돌리거나 앱을 띄우는 에이전트는 한 번에 하나만 띄운다.** git-workflow.md "워크트리를 쓸 때 주의"에 적힌 대로 DB·Redis·8080 포트를 모든 워크트리가 공유한다. 동시에 돌리면 한쪽에서 돌린 테스트가 다른 쪽 데이터를 지우고, 두 번째 `bootRun`은 포트를 잡지 못한다.
- **한 워크트리에 쓰기 에이전트는 하나만 둔다.** 둘을 동시에 돌려 같은 파일을 고치면 나중에 쓴 쪽이 덮어쓰고, **무엇이 사라졌는지 diff로도 드러나지 않는다.** 포트 충돌은 에러로 드러나지만 파일 덮어쓰기는 조용히 지나간다.
- **읽기 전용 에이전트(`Explore`)나 서로 다른 워크트리의 문서 작업은 동시에 돌려도 된다.** 제약은 DB·포트와 같은 파일을 건드릴 때 생기는 것이지 에이전트 수에서 오는 것이 아니다.

## 재작업 루프

- FAIL이면 agent2에게 주는 것은 **FAIL 항목과 재현 명령만**이다. 검증 로그 전체를 주면 "검증을 통과시키는 법"을 역으로 맞추게 된다. 고쳐야 할 것은 코드이지 검증 결과가 아니다.
- **같은 GOAL 항목이 2회 FAIL이면 멈추고 사용자에게 보고한다.** 세 번째 시도가 통하는 경우보다 GOAL이나 접근이 틀린 경우가 많다. 그때 필요한 것은 재시도가 아니라 사용자의 판단이다.
- 전 항목 PASS여도 오케스트레이터가 직접 재확인한다. `git diff --staged`와 `git status --short`를 보고, GOAL에 적힌 검증 명령 중 최소한 빌드·테스트는 직접 돌린다.
  - 빌드·테스트는 `./gradlew cleanTest build`로 돌린다. 입력이 그대로면 Gradle이 test를 UP-TO-DATE로 건너뛰어, verify가 돌린 결과를 다시 보는 것에 그친다. SHI-156에서 verify는 전 항목 PASS였지만 `cleanTest build`에서 DB 연결 고갈로 21건이 실패했다(`.claude/rules/testing.md` DB 연결 수 항목).
  - **implement 보고에서 verify가 볼 수 없는 두 가지를 확인한다.** verify는 보고를 받지 않으므로 여기서만 확인된다.
    - 버그 수정이면 재현 테스트의 **수정 전 실패 출력**이 있는지 본다(`.claude/skills/spec/SKILL.md` 작업 유형별 기존 테스트). 없거나 의심되면 수정을 잠시 빼고 그 테스트를 돌려 실패를 확인한 뒤 원복한다.
    - `## 참고`의 따라 할 기존 코드와 **다르게 짠 곳과 이유**를 diff와 대조한다. 이유가 rules와 맞지 않으면 재작업으로 돌린다.

## 위임하지 않아도 되는 경우

기준은 하나다. **에이전트에게 설명하는 비용이 직접 하는 비용보다 큰가.**

- 한 줄 조회: `git status`, `git log`, DB 조회, 파일 한 개 읽기
- 사용자 질문에 대한 답변. 코드를 고치지 않는 설명은 파이프라인을 태울 것이 없다
- 코드 변경 없이 문서 몇 곳을 고치는 간단한 작업. 오케스트레이터가 직접 고친다

단 **수정이라면 이슈와 워크트리는 그대로 만든다.** 생략하는 것은 위임이지 브랜치 규칙이 아니다. git-workflow.md는 AI에게 예외를 두지 않는다.

## 단계를 건너뛸 때

- **사용자가 단계를 건너뛰라고 명시적으로 지시하면 따른다.** 이것은 기준 완화가 아니라 사용자의 선택이다.
- **에이전트가 스스로 건너뛰지는 않는다.** "이번 건은 간단해서" 같은 판단으로 검증을 빼면, 빼도 되는 경우를 매번 스스로 정하게 되어 절차가 남지 않는다.
