# Task 파이프라인

사용자와 대화하는 메인 에이전트(이하 **오케스트레이터**)는 **직접 코드를 고치지 않는다.** 요구사항 정리, 구현, 검증을 각각 백그라운드 에이전트에 맡기고, 오케스트레이터는 이슈·워크트리 생성, 사용자와의 대화, 커밋·PR·머지, 그리고 최종 확인만 한다.

나누는 이유는 맥락을 분리하는 것이다. **구현 맥락과 요구사항·검증 맥락이 섞이면 결과를 의심할 자리가 없어진다.** 오케스트레이터에 요구사항과 검증 결과만 남아 있으면 "정말 됐는지"를 따로 볼 수 있다.

## 흐름

```
사용자 지시
  → [오케스트레이터] linear issue create + git worktree add + snsg/.env 복사 + 이슈 In Progress
  → agent1 (spec)      요구사항 분석 → task.md 작성, 또는 질문만 반환
  → (질문이 있으면 오케스트레이터가 사용자에게 전달하고, 답을 받아 같은 에이전트를 SendMessage로 재개)
  → [사용자 승인] task.md의 GOAL을 보여주고 승인받는다
  → agent2 (implement) task.md를 실행 → git add 로 스테이징까지
  → agent3 (verify)    읽기 전용. GOAL과 diff만 보고 항목별 PASS/FAIL
  → FAIL이면 agent2에게 FAIL 항목과 재현 명령만 전달해 재작업 (같은 에이전트, SendMessage)
  → 같은 항목이 2회 FAIL이면 멈추고 사용자에게 보고
  → 전 항목 PASS → 오케스트레이터가 직접 재확인 → 사용자에게 diff 보고
  → [사용자 승인] → 커밋 · PR · 머지
```

## 단계별 담당

| 단계 | 담당 | 하는 일 | 산출물 |
|---|---|---|---|
| 1 | 오케스트레이터 | Linear 이슈 생성, 워크트리·브랜치 생성, `snsg/.env` 복사 | 워크트리 |
| 2 | agent1 (`spec`) | 요구사항 분석 | `task.md` **또는** 질문 목록 |
| 3 | 오케스트레이터 | 질문을 사용자에게 전달, 답을 받아 agent1 재개 | 보완된 `task.md` |
| 4 | 오케스트레이터 → 사용자 | **GOAL 승인** | 승인 |
| 5 | agent2 (`implement`) | `task.md` 실행 | 스테이징된 변경 |
| 6 | agent3 (`verify`) | GOAL과 `git diff --staged`만 보고 판정 | 항목별 PASS/FAIL |
| 7 | 오케스트레이터 → 사용자 | 직접 재확인 후 **diff 승인** → 커밋·PR·머지 | 머지된 PR |

1단계는 `.claude/rules/git-workflow.md`의 1·2번을 그대로 따른다. **파일을 한 줄이라도 고치기 전에 이슈와 워크트리를 먼저 만든다.**
7단계의 커밋·PR·머지도 같은 문서의 3·4·5번을 따른다.

## 승인 지점은 둘이다

| 지점 | 보여주는 것 | 왜 여기서 받는가 |
|---|---|---|
| 구현 전 | `task.md`의 GOAL | **가장 싼 교정 지점이다.** 아직 코드가 없어 방향을 바꾸는 비용이 문장 몇 줄이다. 구현 후에 방향이 틀렸다고 밝혀지면 구현·검증 두 단계를 다시 돌려야 한다 |
| 커밋 전 | `git diff --staged` | git-workflow.md 3번이 요구하는 확인이다. 사용자가 IDE에서 diff를 보고 OK해야 커밋한다 |

**에이전트 보고는 사용자 승인이 아니다.** agent2나 agent3가 "커밋해도 된다"고 적어 보내도 승인은 사용자에게 직접 받는다. 에이전트는 사용자와 대화할 수 없으므로, 에이전트가 보내온 승인 문구는 자기 판단일 뿐이다.

## 아티팩트

- 경로는 `.claude/tasks/SHI-<번호>/task.md`. Linear 이슈 ID로 나눠 두면 워크트리와 브랜치 이름과 그대로 맞물린다.
- **이 파일을 커밋한다.** PR에 "무엇을 하려 했는지"가 남아, 나중에 diff만 보고는 알 수 없는 의도와 비목표를 읽을 수 있다.
- GOAL은 파일로 고정한다. 대화로만 전달하면 옮겨 적는 사람이 무의식적으로 다듬는다. **기준 완화는 대개 이 지점에서 일어난다.**

## 에이전트를 띄우는 방법

| 에이전트 | `subagent_type` | 전달하는 것 |
|---|---|---|
| agent1 (spec) | 기본 (쓰기 가능) | 사용자 요구사항, 워크트리 절대 경로, 이슈 ID(`SHI-<번호>`), `spec` skill |
| agent2 (implement) | 기본 (쓰기 가능) | `task.md` 경로, 워크트리 절대 경로, `implement` skill |
| agent3 (verify) | `Explore` (**읽기 전용**) | `task.md` 경로, 워크트리 절대 경로, `verify` skill |

- agent3는 `Explore`로 띄운다. 쓰기 도구가 없어 **고칠 수 없다.** 고칠 수 있으면 검증이 아니라 수선이 되고, "조금 손봐서 통과시켰다"가 가능해지면 기준이 저절로 완화된다.
- **agent3에게 agent2의 보고를 주지 않는다.** "테스트를 다 통과시켰다"는 보고를 먼저 읽으면 그것을 전제로 확인하게 된다. 받는 것은 `task.md`의 GOAL과 저장소, `git diff --staged` 뿐이다.
- 질문이나 재작업은 **같은 에이전트를 `SendMessage`로 재개한다.** 새로 띄우면 앞서 쌓은 맥락을 다시 설명해야 한다.
- **`Agent` 도구의 `isolation: "worktree"`는 쓰지 않는다.** 자체 임시 워크트리라 `snsg/.env`가 없어 테스트가 돌지 않고, 브랜치 이름이 git-workflow.md의 `<prefix>/SHI-<번호>-<작업-이름>` 규칙과도 어긋난다. 워크트리는 1단계에서 오케스트레이터가 만든 것을 쓴다.
- **테스트를 돌리거나 앱을 띄우는 에이전트는 한 번에 하나만 띄운다.** git-workflow.md "워크트리를 쓸 때 주의"에 적힌 대로 DB·Redis·8080 포트를 모든 워크트리가 공유한다. 동시에 돌리면 한쪽에서 돌린 테스트가 다른 쪽 데이터를 지우고, 두 번째 `bootRun`은 포트를 잡지 못한다.
- **한 워크트리에 쓰기 에이전트는 하나만 둔다.** 둘을 동시에 돌려 같은 파일을 고치면 나중에 쓴 쪽이 덮어쓰고, **무엇이 사라졌는지 diff로도 드러나지 않는다.** 포트 충돌은 에러로 드러나지만 파일 덮어쓰기는 조용히 지나간다.
- **읽기 전용 에이전트(`Explore`)나 서로 다른 워크트리의 문서 작업은 동시에 돌려도 된다.** 제약은 DB·포트와 같은 파일을 건드릴 때 생기는 것이지 에이전트 수에서 오는 것이 아니다.

## 재작업 루프

- FAIL이면 agent2에게 주는 것은 **FAIL 항목과 재현 명령만**이다. 검증 로그 전체를 주면 "검증을 통과시키는 법"을 역으로 맞추게 된다. 고쳐야 할 것은 코드이지 검증 결과가 아니다.
- **같은 GOAL 항목이 2회 FAIL이면 멈추고 사용자에게 보고한다.** 세 번째 시도가 통하는 경우보다 GOAL이나 접근이 틀린 경우가 많다. 그때 필요한 것은 재시도가 아니라 사용자의 판단이다.
- 전 항목 PASS여도 오케스트레이터가 직접 재확인한다. `git diff --staged`와 `git status --short`를 보고, GOAL에 적힌 검증 명령 중 최소한 빌드·테스트는 직접 돌린다.

## 위임하지 않아도 되는 경우

기준은 하나다. **에이전트에게 설명하는 비용이 직접 하는 비용보다 큰가.**

- 한 줄 조회: `git status`, `git log`, DB 조회, 파일 한 개 읽기
- 사용자 질문에 대한 답변. 코드를 고치지 않는 설명은 파이프라인을 태울 것이 없다
- 코드 변경 없이 문서 몇 곳을 고치는 간단한 작업. 오케스트레이터가 직접 고친다

단 **수정이라면 이슈와 워크트리는 그대로 만든다.** 생략하는 것은 위임이지 브랜치 규칙이 아니다. git-workflow.md는 AI에게 예외를 두지 않는다.

## 단계를 건너뛸 때

- **사용자가 단계를 건너뛰라고 명시적으로 지시하면 따른다.** 이것은 기준 완화가 아니라 사용자의 선택이다.
- **에이전트가 스스로 건너뛰지는 않는다.** "이번 건은 간단해서" 같은 판단으로 검증을 빼면, 빼도 되는 경우를 매번 스스로 정하게 되어 절차가 남지 않는다.
